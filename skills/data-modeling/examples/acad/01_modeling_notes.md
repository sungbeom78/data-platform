# 학사관리(수강·성적·연락처) 데이터 모델링 노트

입력: 「데이터 모델링 12분 입문 강의」 발표 자료(학생·학과·과목·교수·수강성적·연락처 사례) + 부록 샘플 데이터
범위: 발표 자료 범위 — 한 학기, 분반 없음, 과목당 담당 교수 1명, 학생 연락처 여러 개(본인·보호자·비상)
대상: PostgreSQL 16 · pgModeler 1.1 · 스키마 `acad` · 용어사전은 `meta` 스키마 · 개인정보는 `pi_` 분리

## 1. 관리 대상 (엔터티 후보 → 확정)

| 후보 | 실체 판단 | 확정 |
|---|---|---|
| 학과 | 학생이 속하는 조직. 생성·폐지 관리 대상 | ✅ department |
| 교수 | 과목을 담당하는 사람 | ✅ professor |
| 학생 | 핵심 관리 대상 | ✅ student |
| 과목 | 개설 과목. 학점을 가짐 | ✅ course |
| 수강성적 | 학생과 과목의 관계 + 그 관계에만 붙는 성적 | ✅ enrollment (교차 엔터티) |
| 연락처 | 학생 1명에 여러 개. 주체·유형이 다양 | ✅ contact |
| 담당교수(열) | 과목의 속성 → 교수 엔터티로 참조 | 과목.교수 FK |
| 현재 전화번호(열) | 발표의 문제 원인. 연락처 행으로 이동 | contact 로 흡수 |

## 2. 업무 규칙 (입력에서 추출)
- 학생은 정확히 한 학과에 속한다. (학과 1 — N 학생)
- 학생은 여러 과목을 수강하고, 과목은 여러 학생이 듣는다. 성적등급은 "이 학생이 이 과목을" 들은 사실에 붙는다. → 수강성적 교차 엔터티, PK = (학생, 과목)
- 과목에는 담당 교수가 1명이다. (교수 1 — N 과목)
- 학생에게 연락처가 여러 개 있을 수 있고, 본인 외 보호자·비상 연락처가 포함된다. (학생 1 — N 연락처)
- 이수학점은 과목의 속성, 성적등급은 수강성적의 속성이다. 서로 다르다.
- 같은 학생의 전화번호가 행마다 반복되면 안 된다. 연락처의 기준은 contact 한 곳이다.

## 3. 같은 사실이 여러 곳에 있을 위험 → 기준 결정
| 사실 | 기준 위치 | 변경 규칙 |
|---|---|---|
| 학생 이름 | pi_student.stud_nm | 여기만 수정 |
| 학생 전화번호·주소 | pi_contact.contact_val (연락처 행 단위) | 행 추가/수정/종료 |
| 담당 교수 이름 | pi_professor.prof_nm | 과목에는 교수 ID만 |
| 과목 학점 | course.credit | 수강성적에 복사하지 않음 (향후 "이수 당시 학점" 보존이 필요해지면 enrollment에 스냅샷 컬럼 추가 — 반정규화, 이유 기록) |

## 4. 시간과 변화
- 이번 범위는 한 학기라 학기 엔터티를 두지 않는다. 대신 enrollment 에 `term_cd`(학기코드)를 넣지 않고 **열린 질문**으로 남긴다.
- 연락처는 바뀐다. 이력 테이블 대신 `use_yn` + `updated_at` 으로 현재값만 관리(범위 결정). 이력이 필요해지면 `contact_hist` 추가.
- 성적은 확정 후 정정될 수 있다. `updated_at` 으로 추적, 정정 이력은 범위 밖.

## 5. 향후 변화 시나리오
1. **여러 학기**: enrollment PK에 term 추가 → (stud_id, course_id, term_cd). 지금 구조에서 컬럼 하나 추가로 대응 가능.
2. **분반·공동강의**: course 와 professor 를 N:M 으로 바꾸는 교차 엔터티 `course_professor` 필요. 지금은 course.prof_id 1개.
3. **재수강**: 1번과 함께 자연 해결(학기가 다르면 다른 행).
4. **보호자 연락처의 보호자도 관리 대상이 되면**: contact.subject_cd 를 넘어 guardian 엔터티 분리.

## 6. 식별자 전략
- 모든 테이블 대리키 `bigint IDENTITY` + 업무 자연키 UNIQUE (학생번호·학과코드·과목코드·교수번호).
- 교차 엔터티 enrollment 는 (stud_id, course_id) 복합 PK — 대리키 없이도 의미가 명확하고 중복 수강을 PK가 막는다.

## 7. 개인정보 식별
| 컬럼 | PI 유형 | 처리 |
|---|---|---|
| 학생명 | 성명 | pi_student 로 분리 |
| 교수명 | 성명 | pi_professor 로 분리 |
| 연락처내용(전화·주소) | 연락처 | pi_contact 로 분리 (contact 본 테이블에는 주체·유형·비상여부만) |

## 8. 코드 관리
- 연락처주체(본인·어머니·아버지·보호자·기타), 연락처유형(휴대전화·집전화·이메일·주소) → 코드 테이블 (늘어날 수 있음)
- 성적등급(A+ A0 B+ B0 C+ C0 D+ D0 F) → CHECK 제약 (9개, 거의 안 바뀜)

## 9. 열린 질문 (게이트 2에서 확인)
- Q1. 교수도 학과에 소속되나요? (발표 자료에는 없음 — 이번엔 미포함, 필요 시 professor.dept_id 추가)
- Q2. 학생 상태(재학·휴학·졸업)가 필요한가요? (미포함)
- Q3. 학기 구분을 지금 넣어둘까요? (미포함, 시나리오 1 참고)
